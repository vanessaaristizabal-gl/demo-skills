What the tags mean. Each tag says who creates or changes the files in that place, so you can see where every piece of data comes from. you you write it by hand. page the web page saves it when you click. assistant Claude Code or Codex writes it when you ask. The page never calls a model or Jira, so the handoffs between page and assistant are files you can open.

The two skill folders are independent copies: each harness reads only its own, so changing a skill means changing it in both. The skills did not turn into agents: a skill is the know-how (a folder of instructions), an agent is Claude Code or Codex running it. The pipeline only decides which skill each agent reads, and when. The Codex copies add agents/openai.yaml (its display name and default prompt) and a local-app.md contract that spells out the file formats.

Shared by both

  • app/ pageserver.mjs (no dependencies, no credentials), index.html, app.js, data.js, draft.js (builds a ticket draft from an item; used by the page and the server).
  • samples/ youtranscripts/ is the pre-loaded meeting; new-meetings/ holds transcripts in several scenarios (reversals, bug-only, Spanish, nothing agreed) to hand to the assistant.
  • inbox/ page assistantA meeting from the loaded file (title and date read from its header), then its note and backlog items once processed.
  • drafts/ assistant pageTemporary: one ticket draft per item, only until its ticket exists. Rewritten when the item is edited, deleted after creation.
  • edits/ pageYour edits to backlog items, one overlay per item. The original item is never changed.
  • approvals/ page assistantAn approved draft, then the Jira key once created.
  • manual/ assistantOne file per backlog item, written automatically: a draft section, or “not needed” with its reason.
Skill or agent? The skill is the folder; the agent is the assistant that reads it. Stage 1 is one agent running meeting-notes; stage 2 is two agents (or two steps) running manual-writer and the ticket-writer draft at the same time. Anatomy of a skill. A folder with a SKILL.md. Its name and description are always visible to the assistant, which decides when to use it. The body loads only when the skill is used, and references/ files only when the body asks for them. That keeps the context small.

From the prompt to the ticket

  1. Start. you Open Claude Code or Codex in the folder and say “start the demo”.

    The assistant reads CLAUDE.md or AGENTS.md and starts the local server.

  2. Hand over the meeting. you Give the assistant the transcript file in the chat, or load the file with + Add meeting note in the page. The file is the only input: title and date come from its header.

    From the chat the assistant creates inbox/<id>.json itself. From the page it is saved there as pending. Claude uses its session watcher; Codex's helper reports pending files during an active demo turn. If that Codex turn has ended, say “procesa las reuniones pendientes” to resume.

  3. Extract. assistant The meeting-notes skill runs first.

    It writes the note and the backlog items into the same file. The page shows them in a few seconds.

  4. Fan out, in parallel. assistant manual-writer writes manual/ and the ticket-writer draft writes drafts/, both for every new item, with no extra request.

    Neither waits for the other: both depend only on the items.

  5. Review and edit. you page Open an item, Review draft.

    You can edit the backlog item; saving rewrites its draft file so the ticket always follows the row. Nothing is created.

  6. Approve. you Approve and create ticket.

    The page saves approvals/<id>.json as approved and the item is locked. Still nothing in Jira.

  7. Create. you assistant jira Say “create the approved tickets”.

    The assistant checks the owner in Jira, creates the ticket in GIH with the Jira connector, and writes the key into the approval file and deletes the temporary draft.

  8. See the result. page The Backlog shows the key as a link to Jira.

    The Manual tab and the Manual column were already filled in the parallel step.

The page never calls a model or Jira. Everything that needs judgment or access goes through the assistant, and every handoff is a file you can open.

How the flow is orchestrated

Exists in this demo Proposed design, not built yet Human control
LLM
The model (Claude, GPT) that reads text and decides what to write or do next. On its own it cannot open files or call Jira.
Harness
The program around the model that gives it tools, permissions and context. Claude Code and Codex are harnesses.
Agent
The LLM doing a task through a harness: it decides, uses the harness's tools, reads the result and repeats until done. Example: Claude, inside Claude Code, processing a transcript.
Skill
A folder of instructions (SKILL.md) that an agent loads when a stage needs it: the know-how for one job, such as meeting-notes.
CLAUDE.md, AGENTS.md
A file the harness reads at the start of each session. It tells the agent how this project works.
In this demo. The pre-loaded meeting shows a pre-computed result; a meeting added with + Add meeting note is processed by the real skill. The ticket in step 7 is created for real in the Jira project GIH, only after approval, and tickets cannot be deleted. Not drawn: manual-writer branches off the backlog and drafts the manual section for each item (the Manual column); it never writes to Jira.

Certification concept at each step

Tags map each step to the five domains of the Claude Certified Architect – Foundations exam: D1 Agentic Architecture & Orchestration, D2 Tool Design & MCP Integration, D3 Claude Code Configuration & Workflows, D4 Prompt Engineering & Structured Output, D5 Context Management & Reliability. The mapping is ours, from public exam guides.

  1. 1
    Instructions and skills load on demand. D3 Claude Code

    CLAUDE.md or AGENTS.md is read at the start; a skill body loads only when its stage runs. The same pipeline is written once per harness.

  2. 2
    The coordinator owns coverage. D1 Agentic

    If something is missing even though the subagents did their job, the root cause is how the coordinator split and assigned the work. In this demo the assistant plays that role; a dedicated coordinator is still proposed.

  3. 3
    Parallel work, labeled context, a schema. D1 Agentic D4 Prompts & output D5 Context & reliability

    Notes are independent, so they run at the same time and each extractor receives only its own. Every item travels with its source (note, date, timestamp), and the item shape is fixed so later stages can rely on it.

  4. 4
    Structured errors and informed retries. D2 Tools & MCP D5 Context & reliability

    A failure goes back to the extractor with the specific error, not a bare try again. Jira already does this for us: creating GIH-1488 first failed with the exact missing fields, and we asked the user instead of inventing values.

  5. 5
    Fan out after a shared dependency, restrict with permissions. D1 Agentic D2 Tools & MCP

    5a and 5b need only the items, so they run at the same time. The Drafter is never given the create-ticket tool (allowedTools). If you do not want it to use the hammer, do not hand it the hammer.

  6. 6
    Human oversight before an external effect. D1 Agentic D5 Context & reliability

    Creating a ticket changes someone else's system. Nothing is written until a person approves, and the person can correct the draft; edits rewrite it and approval locks it.

  7. 7
    Idempotency and traceability. D5 Context & reliability

    The approval file carries the Jira key, so the same item is never created twice. The audit log makes it possible to rebuild who proposed and who approved.

Coverage today. Real: D3 (project instructions, skills, background watcher), D4 (skills with templates and a fixed item schema), D2 (the Jira MCP and its structured errors). Partial: D1 (sequence plus a parallel fan-out run by one assistant; coordinator, validator and retry loop are not built) and D5 (provenance, idempotency and human escalation exist; there is no handling of transcripts that exceed the context window).

Honest scope

What is real, what is simulated, what it cannot do

Real

  • The skills run when you add a meeting.
  • Drafts follow the team's templates and acceptance-criteria rules.
  • The ticket is created in GIH after approval.

Simulated

  • The pre-loaded meeting result.
  • The Coordinator and the Validator.
  • People, company and BAK tickets are made up.

Limits

  • It lives inside a Claude Code session: one user, session open.
  • Extraction and ticket type are model judgment, so a person reviews each draft.
  • Tickets cannot be deleted. GIH only has Task, Epic and Subtask.
